# Audit phases — what each one examines

Detail for the phases named in the plan. Work them in order; phases 3–5 are
independent of each other.

---

## Phase 1 — Inventory

Enumerate from the codebase itself — the filesystem plus whatever declares the
entry points for this kind of target — never from memory of what got read along
the way. A partial list silently becomes "everything is
fine" for the parts you missed.

- routes / pages / layouts / screens in scope
- components, tables, forms, dialogs, menus, tabs
- API endpoints, server actions, RPC handlers, message consumers
- data models / schema tables the area touches
- permission definitions, roles, policy files, and their seed data
- background jobs, scheduled tasks, side effects

### Name the enumeration unit first

"Routes" is the unit for a web application, and the coverage denominator is
meaningless without one. State the unit in the plan before counting anything:

| Target | Unit |
|---|---|
| Web application | Routes / pages / screens |
| HTTP API or service | Endpoints, by method and path |
| CLI | Commands and subcommands |
| Library or package | Exported public API surface |
| Mobile application | Screens, plus deep-link entry points |
| Data pipeline or worker | Consumers, topics, and scheduled jobs |
| Desktop application | Windows and menu commands |

**"Files I read" is never a valid unit.** It makes the denominator a description
of the auditor's effort rather than of the application, so coverage becomes
unfalsifiable — exactly what the manifest exists to prevent.

A target with no user-facing surface still has a unit: for a library it is the
public API, and the emphasis moves to contract stability, input validation at
that boundary, and error propagation. If no unit fits, say so and ask, rather
than inventing one that nothing can be checked against.

Before concluding a directory is empty: check for symlinks, nested workspaces,
and ignore rules. A file search that follows neither will report zero files for
a full application.

### Record the manifest, and write it down as you go

Record the enumeration as an **inventory manifest** — the items themselves, the
method used, and the command if there was one. A count alone cannot be checked
by anyone, including you; a list makes the coverage denominator verifiable and
lets a later audit re-run the same enumeration and diff it. See
`finding-model.md` §5.

On a large repository the manifest can outgrow the working context before Phase 2
starts. Both ways of coping silently are wrong: a truncated list makes
`discovered` smaller (and rule 18 will confirm the smaller number quite
happily), and summarizing loses the item names that rule 23 needs.

So record items to the deliverable file as they are enumerated rather than
holding them in context. If the enumeration still cannot be completed, that is a
`SAMPLED` mode with `selection_method: "inventory truncated at N items by
budget"` and the command recorded so the remainder is recoverable — **never
`FULL`, and never a quietly shortened `discovered`.**

Inventory may fan out to subagents provided each returns its enumeration command,
so the parent can re-run it and check the totals rather than trusting them.

Every discovered item must end in exactly one state — reviewed, excluded, or
explicitly `not_reviewed`. There is no fourth state: an item accounted for
nowhere reads as fine to every later reader.

### Generated, vendored, and build output

Excluded by default — but the exclusion must name the generator or manifest that
produces the files, not the category: `reason: "generated by prisma generate, see
prisma/schema.prisma"`. A checkable reason is what stops "generated" from
becoming an unbounded label for whatever nobody wanted to read.

Two consequences worth stating, because both are easy to get backwards:

- Including generated output in `items` inflates the denominator, so every real
  audit reports thin `PARTIAL` coverage and `FULL` becomes unreachable.
- A defect found in generated code is reported against its **source of truth** —
  the schema, the `.proto`, the OpenAPI document — since a fix applied to the
  generated file is overwritten by the next build.

For each section record: purpose, entities involved, operations exposed in the
UI (or in the public contract, for an API), operations existing in the backend,
operations that plausibly belong given the entity's nature.

Cross-reference in **both** directions — the mismatches are the highest-value
findings:

- **backend-only** — capability exists server-side but is unreachable from the
  UI or absent from the contract
- **UI-only** — UI element exists but no backend supports it
- **orphaned** — component or route fully implemented but referenced by nothing

## Phase 1b — Authorization sweep

One shallow pass over every mutating endpoint the inventory found — POST, PUT,
PATCH, DELETE, server actions, RPC mutations — asking a single question: **is
there a server-side authorization check on this handler at all?**

Grep and read. Do not trace, do not evidence, do not classify. The output is a
list of handlers to examine properly in Phase 4, plus the handlers that clearly
have no check, which are already candidate P0s.

Why here, before functional verification: Rule 5 ranks a missing server-side
authorization check above everything else, and Phase 4 is otherwise fourth. This
pass costs minutes and means an audit cut short still has its highest-severity
findings. See `SKILL.md` Step 3.

- [ ] Every mutating handler enumerated from Phase 1, not from memory
- [ ] For each: a session or identity read, and a role or ownership check
- [ ] Handlers with neither, listed for Phase 4 with `file:line`
- [ ] Middleware or layout guards noted but **not** counted as the check
      (`security-checklist.md`) — they protect a path, not an endpoint

What leaves this phase is a **candidate list, not findings.** Nothing here is
serialized into the report yet: the sweep answers "is there a check on this
handler" and nothing about whether the check is correct, reachable, or complete.

That distinction matters because the sweep genuinely reads the handler, so its
evidence would qualify as `code-read` and could carry `CONFIRMED` — for the
narrow proposition "no session read and no role check appears in this function".
It would not support the claim the finding actually makes, which is that the
endpoint is exploitable. Promote a candidate in Phase 4, where the flow is traced
end to end and the evidence states what it proves (`finding-model.md` §2).

## Phase 2 — Functional verification

Verify each operation against the implementation and fill the capability matrix
(`report-template.md`).

Default operations: list, detail, create, edit, delete, archive/deactivate,
status change, bulk actions, search, filter, sort, pagination, import, export,
confirmation dialogs, form/payload validation, role-based permissions.

For non-CRUD areas substitute the domain's real verbs (start, cancel, retry,
publish, approve, refund, sync) and keep the same rigor. State which default
columns were dropped and why.

Status values are the `status` enum from `finding-model.md` §3 — `OK` /
`PARTIAL` / `BROKEN` / `MISSING` / `CANNOT VERIFY` — and nothing else. An
operation you could not trace is `CANNOT VERIFY` with its `resolves_when`, never
a phase-local shorthand.

Then work `edge-cases.md`.

## Phase 3 — Architecture

Assess: layering (UI / business logic / data), code duplication, consistency of
comparable implementations, component reuse, form handling, data fetching and
mutation, cache invalidation after mutation, error handling consistency,
loading state consistency, mutation idempotency, race conditions, transactional
consistency, entity dependencies, client-side vs server-side
pagination/filter/sort, N+1 queries, redundant requests, oversized payloads,
I/O bottlenecks, expected Big-O of the problematic operations.

For each significant problem propose a better design **and its trade-offs**.

## Phase 4 — Security

Work `security-checklist.md` in full. Core axes:

- **AuthN/AuthZ** — the surface is protected; every endpoint independently
  protected; authorization not achieved by hiding a UI control; every sensitive
  operation has a server-side check; object access cannot be manipulated via
  ID/URL/API (IDOR/BOLA); roles correct; no privilege escalation; tenant
  isolation holds.
- **Input** — validated client AND server; SQL/NoSQL injection, command
  injection, XSS, HTML injection, template injection, path traversal, unsafe
  file upload, mass assignment, ID manipulation, unvalidated enum/status values.
- **Sensitive data** — over-fetching to the client, secrets in logs, secrets
  reachable in the client bundle, data shown to users lacking rights, data sent
  to third-party hosts.
- **Destructive operations** — authorization, confirmation, double-execution
  protection, idempotency, audit trail, recovery path.

## Phase 5 — UI/UX

Audit as a frequent user of that area would — a daily operator for back-office,
a first-time visitor for a signup flow.

Record each row per section with the same `status` enum as every other phase, so
a UX gap is a finding rather than an impression. The prose form of this list was
unusable: "assess navigation consistency" has no pass or fail.

| Check | What makes it fail |
|---|---|
| Success feedback | After a save, can the user tell it worked without reloading? |
| Error feedback | Is the failure shown, and does the message say what to do next? |
| Loading state | Is there one, and does the control block a second submit? |
| Empty state | Does a zero-row list explain itself, or render a bare header? |
| Destructive distinction | Is delete visually distinct from the primary action, and confirmed? |
| Post-action navigation | Where does the user land after saving, and is it where they came from? |
| Filter/page preservation | Returning from detail: are filters and page intact? |
| Primary action visibility | Is the main action of the screen findable without hunting? |
| Action naming | Do two buttons for the same thing use the same word across sections? |
| Form validation timing | Inline and before submit, or only after a failed round trip? |
| Keyboard operation | Can the primary flow be completed without a mouse? |
| Focus management | Opening a dialog moves focus in; closing it returns focus out. |
| Table readability | Column count, alignment, and what happens to a long value. |
| Long-content overflow | Does a long name or note break the layout? |
| Responsiveness | Does the audited breakpoint set actually work? |
| Click count | Does a routine daily task take more steps than it needs? |
| Modal vs page | Is a long form crammed into a dialog it does not fit? |

The four rows to weight highest are the ones where the user cannot tell **what
just happened, whether it succeeded, why it failed, or what to do next** — those
generate support tickets rather than complaints, so they are usually
under-reported by everyone except the operators.

For a pure API scope, replace this phase with contract ergonomics — error shape
consistency, status codes, message usefulness.

## Phase 6 — Cross-module consistency

Compare comparable modules. Typical divergences: one table sorts and another
does not; one section allows editing and a comparable one does not; differing
confirmation dialogs; differing error reporting; different buttons for the same
action; different post-save navigation; different validation of the same value
type; different pagination/filter/search implementations.

Propose what should be unified — and which existing implementation should
become the standard.

## Phase 7 — Missing functionality

From existing entities, APIs, schema, and business logic, identify absent but
sensible functionality. Label each `ASSUMPTION` unless its need is directly
evidenced by implementation or stated requirements.

## Phase 8 — Prioritization

Assign `severity` and `likelihood` first, then read `priority` off the matrix in
`finding-model.md` §4. Priority is **derived**, not judged separately — this
phase has no priority definitions of its own, because a second set of them is how
a finding ends up `P0` by prose and `P1` by matrix, which the schema rejects as
`PRIORITY_MISMATCH`.

To deviate from the matrix, set `priority_override_reason`. Deviating never
rewrites `severity`.

Each finding carries impact, likelihood, size `S`/`M`/`L`, dependencies.

When findings arrive from parallel work, de-duplicate before prioritizing —
the same root cause often surfaces in several modules and should be ranked once.

When a previous audit exists, classify every earlier finding rather than only
listing current ones: `STILL_OPEN`, `REGRESSED`, `FIXED`, `DISAPPEARED`, `NEW`
(`finding-model.md` §5a). A finding missing from this audit counts as `FIXED`
only if its location was actually re-reviewed; otherwise it is `DISAPPEARED` and
resolves to `CANNOT VERIFY`. Treating the second as the first is how a series of
audits comes to overstate progress.

## Phase 9 — Report

Write it per `report-template.md`, with the test plan and pre-production
checklist from `test-plan.md`.
